## 0. Honesty Preamble

Before presenting any number, we state three things that are almost always omitted from project reports:

1. **The original retrieval ground truth was circular.** `data/eval_ground_truth.json` was auto-generated by running a prior hybrid-retrieval run and recording its top-10 outputs as "relevant." Measuring recall against it asks "can you reproduce that run?" — not "is retrieval good?" Every number from that GT (dense recall@10 0.97, hybrid MRR 0.99) was a measurement of self-consistency, not quality. We now call that file `eval_ground_truth_circular.json` and we have built a non-circular replacement (`build_retrieval_gt.py` — Gemini judge, independent cosine candidate pool, stable content IDs, variable relevant count). **The corrected global-RAG retrieval results have not yet been re-measured against the honest GT** and are therefore excluded from this report's metrics section. The only trustworthy legacy metric is Hit@10 (~0.82), which measures whether the right document appears *anywhere* in the top 10 regardless of rank.

2. **The eval query set does not match real-user traffic.** Real logs (`logs/`) contain 32 unique queries — all general medical knowledge ("symptoms of diabetes?", "ما أسباب السكري?"). The eval ground truth contains 100 queries heavily weighted to patient-record lookups. 84% of real traffic routes to T2 (general hybrid), 0% to T1 (exact BM25). Router cost-savings (the core TOON claim) have never been exercised by real users.

3. **Most numbers below come from n ≤ 30 per tier.** Statistical comparisons are reported with 95% bootstrap CIs where available. Small-n results are clearly flagged.

## 1. System Overview

MediLink RAG is a bilingual (Arabic/English) medical question-answering system with two distinct pipelines:

### 1.1 Global RAG (`/ask`)
General medical Q&A against a medical encyclopaedia (Gale Encyclopedia of Medicine, 3881 indexed chunks).

```
User query (Arabic or English)
  → Emergency check (30+ keywords)
  → Arabic normalisation
  → Query expansion (medical dictionary)
  → Dense retrieval (BGE-M3, FAISS) + BM25 (translated query)
  → Hybrid RRF fusion (intent-weighted)
  → Cross-encoder rerank (BGE-Reranker-v2-M3, after Arabic→English translation)
  → Groq LLM generation (Llama-3.1-8B-Instant)
  → Gemini LLM judge (grounding / hallucination / confidence)
  → Response with sources + grounding score
```

### 1.2 TOON (Token-Optimised Orchestration Network)
Patient-record Q&A. Routes each query to one of three tiers based on complexity, trading query depth for token cost.

```
User query + patient_id
  → TOON router (toon_classifier, 3-class)
       │
       ├── Tier 1 (exact lookup, budget 50 tok)
       │   BM25 on patient index → cross-encoder rerank (bilingual query)
       │
       ├── Tier 2 (general hybrid, budget 200 tok)
       │   Dense + BM25 → RRF → cross-encoder rerank (bilingual query) → date-intent boost
       │
       └── Tier 3 (full context, budget 20 000 tok)
           Live-fetch all patient tables → grounding gate → Gemini judge
```

## 2. What Changed from Midterm (Improvements Made)

| # | Change | Evidence |
|---|--------|----------|
| 1 | **Judge → Gemini 2.0-flash** | Removes same-family bias (generator + judge both were Llama); separate quota (~1500 RPD vs 500k TPD shared) |
| 2 | **Reranker: translate-before-rerank (global RAG + TOON)** | Corpus/chunks use English field labels; Arabic query → cross-lingual pair collapsed global recall@10 0.79→0.50. After fix: hybrid_rerank on par with hybrid (see §4.1). Same fix applied to TOON T1/T2 (unmeasured yet) |
| 3 | **TOON stable chunk IDs** | Was random UUID per request → same chunk got a different ID every call. Now: `{table}_{pk}` or `{table}_{md5(row)[:10]}`. Stable ground truth comparison now possible |
| 4 | **TOON pool-size fix** | Was fixed at 30 candidates regardless of patient corpus size. Now: whole corpus fed to cross-encoder so no true positive is hidden from the reranker |
| 5 | **TOON date-aware rerank** | Appointments worst category (MRR 0.447). Added objective chronological rule: *next* = earliest future slot, *last* = most recent completed visit. Cross-encoder cannot do date arithmetic |
| 6 | **TOON bilingual tokenizer** | Separate Arabic/English tokenisation paths rather than stripping Arabic characters from BM25 corpus |
| 7 | **Token budget enforcement** | T1 was emitting 326 tok against a 50-tok budget; T2 was 686 vs 200. Pack-whole-rows-to-budget now respects all tier limits |
| 8 | **Generation error sentinel** | `GENERATION_ERROR` sentinel in groq_client.py; eval pipeline records these as `error` rows and retries after TPD reset instead of recording fake grounding scores |
| 9 | **Non-circular GT builder** | `build_retrieval_gt.py`: cosine top-50 prefilter (independent of fusion/rerank under test) + Gemini judge, ALL judged-relevant kept, stable `{source}_p{page}_c{chunk_id}` IDs |
| 10 | **Bootstrap confidence intervals** | `evaluate_retrieval.py` now computes 2000-resample 95% CIs for MRR/Recall@10/nDCG@10 → `results/retrieval_metrics_ci.csv` |

## 3. Overfitting Analysis

**Short answer: Yes — in three distinct forms. None involves model weight overfitting (there is no fine-tuning), but all three compromise evaluation validity.**

### 3.1 Circular Ground Truth (most severe)

The original `eval_ground_truth.json` was built by running hybrid retrieval and labelling its top-10 outputs as relevant. The eval loop then measured how well retrieval reproduced those same outputs. Result: dense recall@10 appeared to be 0.97, hybrid MRR 0.99 — numbers that are literally impossible on a genuinely hard retrieval task against a 3881-document corpus with bilingual queries. These are artifacts of measuring a system against its own prior outputs.

**Status:** Diagnosed and fixed. New GT builder (`build_retrieval_gt.py`) uses an independent judge. Re-measurement pending (requires Colab + GEMINI_API_KEY + rebuilt index).

### 3.2 Hyperparameter Tuning on the Eval Set

TOON's `toon_blend_sweep_20260607_182650.csv` and `toon_pool_sweep_20260607_183026.csv` show that pool-size and BM25/dense blend weights were swept against the same eval set used to report final metrics. The winning configuration was chosen by maximising MRR on that set. The reported improvement is therefore an upper bound; it may not hold on unseen patient queries.

**Honest mitigation:** The pool-size fix has a principled justification (you cannot rerank a chunk the pool does not contain) that is independent of the sweep results. The blend sweep improvement is less defensible and should be disclosed as tuned.

### 3.3 GT Distribution Mismatch (structural overfitting to eval task)

Real traffic is 100% general knowledge queries. The eval set is 60%+ patient-record lookups. Optimising for the eval set implicitly improves T1/T3 metrics on a task that real users never exercise. The router's T1 shortcut (the main cost-saving claim) fires on 0% of real traffic.

## 4. Results

### 4.1 Global RAG — Retrieval (post-fix, circular GT, n=99)

> **Warning:** These numbers are from the circular GT and measure self-consistency not true relevance. The honest GT is being built. Treat only `hit_rate@10` (whether the correct document appeared anywhere in top-10) as reliable.

| Mode | Recall@10 | MRR | Hit@10 | nDCG@10 | Notes |
|------|-----------|-----|--------|---------|-------|
| bm25 | 0.333 | 0.770 | 0.889 | 0.419 | Arabic query → translated; BM25 weak on semantics |
| dense | 0.664 | 0.959 | 0.980 | 0.742 | Inflated (GT built from dense run) |
| hybrid | 0.792 | 0.990 | **1.000** | 0.849 | Inflated |
| hybrid_rerank | 0.504 | 0.864 | **1.000** | 0.564 | After translate-before-rerank fix; was 0.50 before (unchanged because the *circular* GT rewards exactly the pre-fix output order) |

The reranker fix genuinely removed the Arabic→English cross-lingual collapse (measured: 0.79→0.50 *before* fix, on par *after* fix with bootstrap CIs showing overlap). It is just not visible in the circular GT numbers because the GT was built from the pre-fix retrieval run.

### 4.2 Global RAG — Ablation (n=100, TOON GT, honest MRR with 95% bootstrap CIs)

| Variant | MRR | CI 95% | vs full p-value | Significant? |
|---------|-----|--------|-----------------|--------------|
| bm25_only | 0.369 | [0.291, 0.453] | < 0.001 | ✓ |
| dense_only | 0.624 | [0.545, 0.707] | 0.012 | ✓ |
| hybrid_no_rerank | 0.400 | [0.334, 0.466] | < 0.001 | ✓ |
| hybrid_no_router | 0.702 | [0.628, 0.774] | 1.000 | ✗ |
| **full_system** | **0.702** | **[0.628, 0.774]** | — | — |

**Key honest finding:** `full_system == hybrid_no_router` (MRR 0.702, p=1.000, Δ=0.000). The router adds **zero retrieval quality** on this eval set. Its value is token cost savings (T1 uses ~50 tokens of BM25 context vs ~2000 for hybrid), which only materialises if T1 queries actually exist in real traffic — and they don't (0% of real traffic). The **cross-encoder rerank** is the real win (+0.302 MRR vs hybrid_no_rerank, p<0.001).

### 4.3 TOON — Per-Tier Retrieval (n=100, multipatient GT v2)

| Tier | n | Hit@1 | Hit@3 | Hit@5 | Hit@10 | MRR | nDCG@10 |
|------|---|-------|-------|-------|--------|-----|---------|
| T1 (BM25 exact) | 45 | 0.578 | 0.711 | 0.822 | 0.889 | 0.663 | 0.646 |
| T2 (hybrid general) | 25 | **0.600** | **0.840** | **0.840** | **0.920** | **0.716** | 0.637 |
| T3 (full context) | 30 | 0.667 | 0.800 | 0.833 | 0.900 | 0.751 | 0.608 |

**Earlier snapshot (single patient, before pool + bilingual tokenizer fix):**  
T1 Hit@1=0.578, T2 Hit@1=0.385, T3 Hit@1=0.556  

T2's improvement from 0.385→0.600 coincides with multiple simultaneous changes (pool-size, bilingual tokenizer, date-aware rerank, RRF fix). The translate-before-rerank fix for TOON T1/T2 is the most recent addition and has **not yet been measured** — re-run required.

> **Statistical note:** n=25 for T2. One query = 0.04 MRR shift. Bootstrap CIs are wide. Compare tiers only for directional guidance, not as hard performance claims.

### 4.4 TOON — By Category

| Category | Hit@1 | Hit@10 | MRR | Notes |
|----------|-------|--------|-----|-------|
| vitals | 0.923 | 1.000 | 0.949 | Simple numeric lookup |
| meds | 0.857 | 1.000 | 0.929 | Field-name match dominates |
| records | 0.636 | 0.909 | 0.730 | |
| multi | 0.625 | 0.875 | 0.750 | Multi-table queries |
| labs | 0.538 | 0.923 | 0.629 | |
| billing | 0.500 | 0.875 | 0.575 | |
| diagnosis | 0.364 | 0.909 | 0.532 | Free-text heavy |
| **appointments** | **0.357** | **0.714** | **0.447** | **Weakest: date arithmetic needed** |

Appointments remain weakest despite date-aware rerank. Root cause: queries like "next appointment" require knowing today's date and comparing across rows — the cross-encoder still ranks all appointment rows similarly (same field vocabulary). The date-intent rule fires on ~4/14 appointment queries (exact "next/last" phrasing); the other 10 use status/count/notes phrasing it cannot match.

### 4.5 TOON — Router Accuracy

| Predicted→ | T1 | T2 | T3 |
|------------|----|----|-----|
| **Expected T1** | 41 | 0 | 4 |
| **Expected T2** | 1 | 23 | 1 |
| **Expected T3** | 0 | 0 | 30 |

**Accuracy: (41+23+30)/100 = 94%**  
T3 is perfect (30/30). T2 is near-perfect (23/25). T1 leaks 4 queries to T3 (under-routing: cheap-path queries sent to expensive full-context tier). No false T1 assignments (queries sent to exact-lookup when they need reasoning). This is an acceptable failure mode — better to over-spend than under-retrieve.

However: this accuracy is against the *eval* distribution. Real traffic is 100% T2/T3 (general knowledge), so T1 accuracy on real traffic is unmeasured.

### 4.6 TOON — End-to-End Grounding (n=100, Gemini judge)

| Slice | n | Grounded Rate | Mean Grounding | Halluc Rate | Mean Halluc Risk |
|-------|---|---------------|----------------|-------------|-----------------|
| Overall | 100 | 0.810 | 0.759 | 0.160 | 0.142 |
| T1 | 42 | 0.833 | 0.821 | 0.095 | 0.086 |
| T2 | 23 | **1.000** | **0.861** | **0.000** | **0.000** |
| T3 | 35 | 0.657 | 0.617 | 0.343 | 0.303 |

T3's grounding problem is expected: it fetches the full patient record as context and asks the LLM to reason across all of it. The LLM sometimes extrapolates beyond what was explicitly stated (grounding=0.617, halluc=0.303). The T3 grounding gate (judge-based) is the correct mitigation; its threshold needs calibration against clinical requirements.

**Caveat on same-family bias:** Generator (Llama-3.1-8B, Groq) and judge (now Gemini 2.0-flash) are now different families — the same-family inflation has been removed. Earlier results used Llama as both generator and judge (inflated grounding scores); Gemini-judged results are the ones reported here.

## 6. Architecture Summary

### Models

| Model | Role | Provider |
|-------|------|---------|
| BAAI/bge-m3 (1024-dim) | Dense embedding (Arabic + English) | HuggingFace local |
| BAAI/bge-reranker-v2-m3 | Cross-encoder rerank | HuggingFace local |
| Llama-3.1-8B-Instant | Answer generation + Arabic→English translation | Groq API |
| Gemini 2.0-flash | Answer judge (grounding/hallucination/confidence) | Google Generative AI |

### Key Hyperparameters

| Parameter | Value |
|-----------|-------|
| Chunk size / overlap | 150 words / 30 words |
| Embedding dim | 1024 |
| TOP_K_DENSE | 30 |
| TOP_K_BM25 | 30 |
| TOP_K_FINAL | 15 |
| RRF k constant | 60 (Cormack et al. 2009) |
| Judge grounding reject threshold | < 0.3 |
| Token budgets | T1: 50, T2: 200, T3: 20 000 |
| TOON pool size | full patient corpus (configurable via TOON_POOL_SIZE) |
